1. Testing goals

Automated tests protect the application's academic workflows, authorization boundaries, validation behavior, and model calculations. A repeatable test run should provide fast feedback while ensuring test data is isolated from local or production databases.

Current configuration: phpunit.xml selects an in-memory SQLite database for test runs. Feature tests use Laravel's RefreshDatabase trait through tests/Pest.php.

4. Test safety and database isolation

  • PHPUnit's configured test connection is SQLite with :memory: storage. Schema and data exist only for the test process.
  • Feature tests use RefreshDatabase, so each test starts from a migrated clean schema.
  • A shell-level DB_CONNECTION or DB_DATABASE override may replace the configured test values. Verify that overrides point only to disposable test data.
  • Do not point a migration-refreshing test suite at a shared development or production database.
  • Tests that create tokens, users, uploads, enrollments, or catalog records should assert both the expected result and the important failure/no-side-effect behavior.

6. Unit test example

StudentEnrollment::getTotalUnitsAttribute() sums subject units from its loaded many-to-many relation. This is a deterministic calculation, so a unit test can supply an in-memory relation without database setup:

test('student enrollment total units sum the assigned subjects', function () {
    $enrollment = new StudentEnrollment;
    $enrollment->setRelation('subjects', collect([
        new Subject(['units' => 3]),
        new Subject(['units' => 2]),
    ]));

    expect($enrollment->total_units)->toBe(5);
});

A second test verifies that no assigned subjects yields zero. These tests are in tests/Unit/StudentEnrollmentTest.php.

7. Feature test example

The API validation test exercises routing, Sanctum authentication, request validation, JSON response behavior, and absence of an unintended database write:

$this->withToken($token)
    ->postJson('/api/students', [
        'student_number' => 'API-INVALID',
        'first_name' => '',
        'email' => 'not-an-email',
        'course_id' => 999999,
        'year_level_id' => 999999,
    ])
    ->assertUnprocessable()
    ->assertJsonValidationErrors([
        'first_name', 'email', 'course_id', 'year_level_id',
    ]);

$this->assertDatabaseMissing('students', [
    'student_number' => 'API-INVALID',
]);

This verifies the HTTP contract rather than invoking a controller method directly.

8. Test conventions for new changes

  1. Write a test from an observable acceptance criterion.
  2. Cover a successful path and the most important invalid/unauthorized path.
  3. Assert persisted state and absence of partial writes for transactional flows.
  4. Use factories or small explicit fixtures; avoid depending on shared environment records.
  5. Keep tests deterministic: control dates, avoid external network calls, and fake storage/services where appropriate.
  6. Run the focused test first, then the full suite before handoff.
  7. Report failures and environment constraints honestly; do not convert failing checks into silent success.
