Database Schema,
Migrations & Relationships

A practical reference to the student management system's persisted data model, migration history, and Eloquent associations.

Source of truth: Laravel migrations and Eloquent models in this project.

Verification: Every migration currently in the project reported as applied by php artisan migrate:status.

Scope: Core academic data, authentication, and Laravel infrastructure tables.

1. Executive overview

The schema supports student profiles, courses, year levels, subjects, academic-period enrollment, subject selection, and enrollment approval. The newer design separates a student's enrollment in a course and school year from the individual subjects selected for that enrollment.

Important transition note: The migration history creates and evolves the legacy enrollments table, then migration 2026_11_07_000014 creates student_enrollments and subject_enrollments and copies legacy data into them. That migration does not drop the legacy table. Treat the two new tables as the normalized enrollment design; the old table remains in the database for compatibility/history unless a later migration retires it.

7. Schema design notes and operations

  • Normalization: Keep a student profile separate from each academic-period enrollment. Keep subject selection in its own pivot table so a single period enrollment can include multiple subjects.
  • Referential integrity: Use the declared foreign keys. Profile links and approver links are nullable and preserve dependent records when the referenced user/profile placement is deleted; normalized academic records use restrictive deletes to avoid accidental loss.
  • Duplicate prevention: Unique student number, course code, subject code, student/user profile link, period enrollment tuple, and subject-enrollment pair constraints protect key identities.
  • Legacy transition: The older enrollments table still exists and the legacy Eloquent model remains. Applications should consistently use the normalized path for new enrollment workflows unless intentionally supporting legacy behavior.
  • Rollback planning: Migration 014's down method drops the normalized tables and the new catalog columns; it does not reverse the backfilled rows into enrollments. Take a backup and validate data before rolling it back in a populated environment.
