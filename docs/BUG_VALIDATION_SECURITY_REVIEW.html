& Security Review

A source-based review of test results, request validation, authorization boundaries, and security-relevant application behavior.

Application: Laravel 12 student management system.

Review basis: Controllers, routes, middleware, form requests, database constraints, feature tests, and an isolated SQLite test run.

Scope note: Findings describe the checked-in implementation; this is not a production penetration test.

1. Executive summary

The application has broad feature coverage for its student, enrollment, authentication, and API workflows. The isolated test run completed 55 tests: 54 passed and one enrollment assertion failed because the stored date string included a time component. This run used an in-memory SQLite database so it did not depend on the configured MySQL database.

Request validation is present across the main write paths, and role middleware checks both account activation and allowed roles. Enrollment changes use transactions and student self-service scopes cancellation to the signed-in student's own pending enrollment. The security findings and their severity are summarized in the security section.

3. Validation review

Controls observed

  • Write endpoints validate required fields and use uniqueness rules that ignore the current row on update.
  • Related IDs generally use exists checks; enrollment writes further verify that selected subjects are active and match the chosen course/year level.
  • Enrollment school-year values use a defined YYYY-YYYY format; duplicate enrollment checks are backed by application checks and a composite unique database constraint.
  • Student birth dates are constrained to today or earlier; uploaded profile photos are limited to image types and a maximum size.
  • Role and status inputs use allow-lists; free-form search input is bounded by string length and query values are parameterized by Eloquent.
  • Login validates credentials, rejects inactive users, and rate-limits attempts. Password reset and profile deletion validate the relevant credentials.
  • Enrollment updates and approval/cancellation of related subject assignments are wrapped in database transactions.

4. Security review

The application routes and controller access checks were reviewed for authentication, role enforcement, ownership, input validation, and data-retention risks. Security findings are listed below in severity/confidence order.

No confirmed, high-confidence vulnerabilities found. The review covered authentication, role enforcement, student ownership/deletion paths, request validation, query construction, API resources, and Blade output/file handling. This is a source review, not a penetration test.

Positive security controls

  • Admin/staff and student route groups use authentication plus role restrictions; the role middleware rejects inactive accounts.
  • Student self-service enrollment is derived from the authenticated account's linked student profile. Cancellation re-queries through that student's relationship and permits only pending records.
  • The student JSON API is protected by Sanctum and admin/staff role middleware.
  • Login has a five-attempt rate limit; registration accounts begin inactive; enrollment-sensitive changes are transactional.
  • Tests cover unauthenticated API rejection, inactive token rejection, staff denial for user management, student portal separation, and enrollment ownership/cancellation.

Severity labels describe application impact and exploitability in the reviewed code. Confidence indicates certainty that the behavior is present in the cited source.

5. Review limitations and recommendations

  • This is a static/source review plus application feature tests, not a penetration test or deployment/configuration audit.
  • Production database permissions, HTTPS/session cookie configuration, web-server rules, backup/retention policy, and operational secrets were not assessed.
  • Fix the isolated SQLite date assertion and explicitly configure a disposable test database before relying on an unqualified php artisan test command.
  • Review any security finding in context of the intended API/deletion policy before applying changes; preserve existing enrollment-history requirements.

6. Source and reproducibility

Primary review sources include tests/Feature/EnrollmentTest.php, tests/Feature/Api/StudentApiTest.php, phpunit.xml, route definitions, EnsureUserHasRole, login/profile request validation, and the student/enrollment controllers. The isolated full-suite command was:

$env:DB_CONNECTION = 'sqlite'
$env:DB_DATABASE = ':memory:'
php artisan test

The temporary environment overrides were removed after the command completed.
