Controllers, CRUD
Operations & Routes

A code-based reference to the application's web and API routes, controller responsibilities, access controls, validation, and CRUD workflows.

Source of truth: routes/web.php, routes/api.php, routes/auth.php, controllers, and the role middleware.

Route check: Application route list was inspected with php artisan route:list --except-vendor.

Scope: Student management system web application and Sanctum-protected student JSON API.

1. Application structure

Routes map HTTP requests to controller actions. Web controllers generally validate form input, operate on Eloquent models, and return Blade views or redirects with session messages. The API student controller returns JSON resources and HTTP status codes.

routes/web.php ── web/session/CSRF ── role & auth middleware ── Controllers ── Blade / redirect routes/auth.php ─ guest/auth flows ───────────────────── Auth controllers routes/api.php ─── Sanctum token + role middleware ───── API StudentController ── JSON resource bootstrap/app.php ─ registers the "role" middleware alias

4. Enrollment CRUD and approval

EnrollmentController works with the normalized StudentEnrollment model; each record represents one student's course/year-level enrollment in a school year. Selected subjects are stored as related subject-enrollment rows.

ActionBehavior
indexSearch student, course, year level, school year, status, and subjects. Optional filters include student, course, year level, school year, and pending/approved/rejected/cancelled status. Loads related records and paginates 10.
create, show, editShow enrollment form/details. Edit is allowed only while pending (otherwise 403).
storeValidates an existing student, active course/year level, YYYY-YYYY school year, date, and one or more distinct subject IDs. Subjects must be active and assigned to the selected course and year level. Creates enrollment and subjects in a transaction; prevents duplicate student/course/year-level/school-year enrollment.
updateOnly pending enrollments can be edited. Replaces subject assignments and updates enrollment fields atomically in a transaction.
approvePATCH action; only pending records transition to approved. Sets approver and approval time and approves all subject assignments in a transaction.
destroyFor a pending request, marks enrollment and subject assignments cancelled rather than deleting history. Non-pending records are not cancelled.
The route is named destroy and uses HTTP DELETE, but its business behavior is a soft workflow cancellation via status update—not a database delete. Approval is a separate PATCH route.

7. Student JSON API

Defined in routes/api.php as a named api. resource. Every student resource action requires a Sanctum token and the active admin/staff role.

Method and URIRoute name / actionResponse
GET /api/studentsapi.students.indexPaginated collection (15 per page), ordered by last and first name; includes course and year-level data.
POST /api/studentsapi.students.storeValidates and creates a student; returns StudentResource with HTTP 201.
GET /api/students/{student}api.students.showSingle StudentResource with course and year level.
PUT/PATCH /api/students/{student}api.students.updateValidates and updates a student; returns refreshed StudentResource.
DELETE /api/students/{student}api.students.destroyDeletes the student and returns HTTP 204 No Content.
GET /api/userClosure route (no named resource action)Returns the current Sanctum-authenticated user; requires auth:sanctum.

Student API create/update validation requires a unique student number, first and last names, and existing course/year-level IDs. Email, phone, date of birth, and address are optional. Responses are shaped by StudentResource, not raw model serialization.

Behavior difference to note: Web student deletion explicitly blocks when enrollment history exists. The API controller calls delete() directly and does not apply that guard; database foreign-key behavior determines whether a linked student can be deleted.

9. CRUD and validation conventions

  • Validation: Controllers use Laravel request validation. Invalid web form requests redirect back with errors and old input; invalid JSON requests receive Laravel's JSON validation response.
  • Unique updates: Unique keys exclude the current model ID using Laravel's Rule::unique(...)->ignore(...).
  • Route model binding: Parameters such as {student}, {course}, and {enrollment} resolve to Eloquent models. Missing records return 404.
  • Web feedback: Successful changes generally redirect to the list or relevant profile/dashboard with a flash status. Guard failures return field errors or 403.
  • History preservation: Academic enrollment cancellation changes status instead of deleting records; catalog and student web deletes are guarded where history/relations exist.
  • Transactions: Enrollment create/update/approval and related subject changes are transactional to keep parent and subject status/data aligned.
  • API responses: API actions return a JSON resource, 201 for create, and 204 for successful delete. Missing/invalid auth returns 401; role denial returns 403.
