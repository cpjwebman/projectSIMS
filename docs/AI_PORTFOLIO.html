Student Management
System

A role-based academic administration application for student records, course catalogs, subject selection, enrollment review, and student self-service.

Project type: Full-stack web application with authenticated JSON API

Framework: Laravel 12 · PHP 8.2+

Portfolio focus: Product capabilities, implementation highlights, and technical design

Project at a glance

The Student Management System brings core academic administration into one application. Administrators and staff maintain academic records and process enrollment requests. Students can maintain their linked profile, choose eligible subjects, and follow the status of their academic enrollments.

Academic records

Manage students, courses, year levels, subjects, school-year enrollments, and subject assignments.

Role-based experiences

Separate staff/admin management from student self-service, with active-account and role checks.

Enrollment workflow

Collect course and subject choices, prevent duplicate requests, approve requests, and preserve cancellation history.

Operational visibility

Explore date- and status-filtered metrics, monthly activity charts, course counts, and recent requests.

Problem and solution

Academic records connect students to programs, year levels, subjects, and enrollment periods. Keeping these records consistent while supporting both administrative workflows and student access requires clear relationships and permissions.

Solution: A Laravel application with normalized enrollment records, explicit course/year-level subject eligibility, validated CRUD operations, transactional enrollment updates, and distinct role-gated web/API surfaces.

Feature highlights

Academic catalog and student records

  • Create, search, update, and maintain student profiles, courses, year levels, and subjects.
  • Associate subjects with a course and year level, including units and an active/inactive state.
  • Protect referenced records from inappropriate deletion; use deactivation where academic history must remain.

Enrollment from request to decision

  • Group student enrollment by course, year level, and school year.
  • Assign multiple subjects to one enrollment and enforce eligibility against the selected course and year level.
  • Track pending, approved, and cancelled workflows; record approver and approval time.
  • Update enrollment and related subject rows within database transactions.

Student portal and profiles

  • Link a login account to one student profile and restrict portal history to the signed-in student's records.
  • Support profile updates and optional validated profile photo upload/removal.
  • Retain cancelled request history rather than deleting enrollment records.

Reports and data visibility

The staff dashboard summarizes enrollment activity from the normalized student-enrollment data. Filters cover calendar year, month, and enrollment status.

Dashboard sectionInformation presented
Summary cardsUsers, students, courses, period enrollments, pending and approved requests, students without enrollments, and subjects.
Activity chartsMonthly enrollments by enrollment date, status distribution, monthly request creation activity, and enrollment distribution by course.
Course summaryCourse names, codes, and counts matching the selected filters.
Recent activityUp to eight recent matching enrollment records, with student, course, subjects, date, and status.

The current dashboard is an interactive web report. It does not expose a report export/download endpoint.

API capability

A JSON student-resource API supports list, create, retrieve, update, and delete. Requests are authenticated with Sanctum bearer tokens and restricted to active administrator/staff accounts. Student responses use a resource representation with related course and year-level data.

MethodEndpointPurpose
GET/api/studentsPaginated student list.
POST/api/studentsCreate student.
GET/api/students/{student}Retrieve student.
PUT/PATCH/api/students/{student}Update student.
DELETE/api/students/{student}Delete student.

Technical implementation

Laravel 12PHP 8.2+Eloquent ORMBladeLaravel SanctumViteSQLite / MySQL-compatiblePest
  • Application: Laravel controllers and resource routes for web CRUD, student self-service, and authentication.
  • Data: Migrations define foreign keys, uniqueness, indexes, and normalized student/subject enrollment tables.
  • Authorization: Route middleware requires authenticated users with permitted roles and active accounts.
  • Validation: Requests validate unique identifiers, related records, status choices, dates, subject eligibility, and uploaded image type/size.
  • API: Sanctum authentication and a dedicated StudentResource control access and JSON shape.
  • UI: Blade views with responsive layouts and dashboard charts.

Quality and verification

Feature tests cover enrollment workflows, student portal scoping, API CRUD/authentication, dashboard metrics, profile operations, and role access. In the reviewed isolated SQLite run, 54 tests passed and one enrollment test failed on a date-format assertion: it expected a date-only value while SQLite returned the same date with a midnight time component. This is a test portability issue, not evidence that the enrollment update failed.

Security review of the inspected routes, authorization, validation, query construction, API resource, and view output found no confirmed high-confidence vulnerabilities. Source review is not a substitute for deployment configuration review or penetration testing.

Run locally

Typical local setup requires PHP, Composer, Node.js/npm, application environment configuration, migrations, and built frontend assets.

composer install
php artisan key:generate
npm install
php artisan migrate --seed
npm run build
php artisan serve

Configure .env and database settings for the intended environment. Tests should use a dedicated disposable test database.
