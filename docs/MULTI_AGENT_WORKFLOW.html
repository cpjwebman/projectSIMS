Engineering Playbook | Agent Collaboration

Multi-Agent Workflow
& Specialized Agents

A practical, review-gated collaboration model demonstrated with the Student Management System enrollment workflow.

Example system: Laravel 12 student management application

Demonstration: Student enrollment request through staff approval

Goal: Parallelize independent work while keeping implementation, tests, and decisions coordinated

1. What “multi-agent” means here

A multi-agent workflow assigns bounded engineering responsibilities to specialized AI agents. Each agent receives a defined objective, relevant project context, expected output, and a stop condition. A human or lead agent coordinates dependencies, integrates changes, and makes final acceptance decisions.

Important: This document describes a workflow and demonstrates how specialized agents can collaborate. It does not claim that a multi-agent runtime, orchestration service, or autonomous agent system is installed in this Laravel application.

4. Coordination rules and gates

  1. One source of truth: The repository and approved task contract define behavior; agents do not invent schema, role policy, or route semantics independently.
  2. Bounded tasks: Each agent owns a concrete deliverable, files or subsystem, and acceptance/stop condition.
  3. Explicit dependencies: Schema/API contract precedes dependent backend/UI work. Independent review can proceed once the changed surface is stable.
  4. Clear file ownership: Avoid simultaneous edits to the same files. Share interfaces first; integrate sequentially when changes overlap.
  5. Review findings are evidence: Report source location, impact, confidence, and reproduction conditions. A reviewer does not silently alter behavior.
  6. Lead agent owns integration: Re-read combined changes, resolve contradictions, run the focused tests, and report incomplete checks.
  7. Protect data and credentials: Use an isolated test database, do not expose secrets, and do not apply migrations or destructive operations to a shared environment without approval.
Gate A — Ready to implement: Acceptance criteria, data contract, route, authorization rule, and failure behavior are agreed.
Gate B — Ready to merge: Focused tests pass, security findings are triaged, no unrelated changes are included, and documentation reflects actual behavior.

5. Demonstration: enrollment request and approval

Example request: A student selects an active course and year level, chooses eligible subjects for a school year, submits an enrollment request, and an authorized staff member approves it.

Step 1 — Requirements analyst defines the contract

  • Only the signed-in student's linked profile may create a self-service enrollment.
  • Course and year level must be active. At least one distinct subject must match both.
  • At most one enrollment is allowed per student/course/year-level/school-year tuple.
  • Submission creates a pending enrollment and pending subject assignments.
  • Only authorized staff/admin may approve a pending request; approval records approver/time and updates its subject assignments.
  • Only pending requests may be cancelled; cancellation preserves the record and history.

Step 2 — Data specialist maps the existing model

Inspect the current schema before proposing new tables. The application already has student_enrollments and subject_enrollments, including a period uniqueness constraint and subject-assignment uniqueness. The data agent should flag nullable year-level uniqueness semantics and existing legacy enrollments migration history rather than introducing a duplicate design.

Step 3 — Backend and UI specialists implement to one contract

The backend uses the student portal routes and StudentPortalController for self-service, and the admin/staff enrollment resource plus approval route for review. The UI specialist can work in parallel on the student selection form and staff review states once endpoint fields and validation errors are agreed.

Step 4 — QA agent turns rules into evidence

Valid eligible subject selectionRedirect success; one pending student enrollment and expected pending subject rows.

Duplicate period enrollmentDuplicate error; only one matching enrollment remains, including under competing requests where supported.

Edit/approve a non-pending requestExisting state is retained; request is rejected or reports it has already been reviewed.

Step 5 — Security reviewer checks boundaries

Trace request user to student profile; confirm ownership is enforced server-side, role middleware covers staff approval, eligible subjects are queried against active placement, validation errors do not disclose unrelated records, and state updates remain transactional. Deliver a read-only finding list with evidence.

Step 6 — Lead integrates, docs agent records behavior

The lead inspects both parallel changes together, runs the enrollment and portal feature tests using a disposable database, resolves issues, and confirms no conflicting route or validation assumptions remain. Documentation records the real route names, statuses, validation, and any unimplemented behavior.

7. Sample task briefs

Backend brief

Objective: implement only the agreed enrollment request contract.
Inspect existing models/migrations before editing.
Keep student ownership server-side; validate active and eligible subjects.
Persist parent and subject rows transactionally.
Add focused tests for success, invalid subject, and duplicate period.
Do not change routes or schema outside the approved design.
Stop when focused tests pass; report changed files and assumptions.

QA brief

Objective: verify the enrollment acceptance criteria against the implementation.
Use an isolated test database only.
Cover invalid/ineligible subjects, duplicate requests, ownership,
pending-only cancellation/edit, and approval metadata.
Do not modify application code; report exact test results and failures.

Security-review brief

Objective: read-only review of enrollment authorization and input boundaries.
Trace routes, role middleware, ownership checks, validation, transactions,
and data exposure. Report only confirmed/high-confidence findings with
file and line evidence, impact, and confidence—or explicitly report none.
Do not make code changes.

8. Success measures

  • Each acceptance criterion maps to an implementation and a test or a recorded limitation.
  • Parallel agents share one stable contract and do not overwrite each other's changes.
  • Authorization and ownership are verified at the server boundary, not only in the UI.
  • Test runs are isolated and repeatable; failures are reported rather than hidden.
  • Final documentation describes shipped behavior without overstating automation or review coverage.
